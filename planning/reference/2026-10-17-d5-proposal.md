# D5 proposal

- **Status:** proposal for the owner (D37). No code was written for it.
- **Basis:**
  - `main` at `3953e0c`.
  - Three read-only traces made by subagents of cloud-claude, one per area (chat and user, settings and app, location). Each went from a view model's call site through the use case and `data:repo` down to a transport, and gave file and line for each throw.
  - cloud-claude checked the claims the proposal leans on. Those checks are marked "checked" below.
  - The `data:repo`, platform and transport paths were **read, not run**.
- **Words used here:**
  - **Uncaught:** the call runs in a `viewModelScope.launch` with no `try` and no handler. On Android and iOS the app ends. The desktop TUI logs it (`apps/desktop/tui/.../Main.kt:53`), and so does the board's TUI when it has a terminal (`Posix.kt:184`); both keep running. The Compose desktop runs on the Swing main thread, whose handler prints the trace.
  - **The chat catch-all:** the `try` around `ChatViewModel.sendMessage` (`ChatViewModel.kt:172`, catch at `:319`). It covers every `/command` and every send, and shows "Failed to send: ${e.message}" (checked).

## The rule this proposal applies

1. **An `Outcome`** with the feature's failure (D5, D23), when the failure is one the user can cause or act on, or one that leaves what the screen shows wrong. The failure carries facts; the view model owns the text (D24).
2. **The exception stays**, when it is a programming error (a `require` on input that was already validated, an `error()` no caller can reach), a library failure with no remedy (a missing crypto provider), or a cancellation.
3. **A fix in `data:*`, with the contract unchanged**, when the failure belongs to a side step that must not fail the command (a place name for a bookmark), or when the data layer breaks a rule it already has (a swallowed cancellation).
4. **Every proposed `catch` rethrows `CancellationException` first** (CONVENTIONS, Failures).

## Part 2. Observers whose read fails

**Today:** an exception from a read ends the observer's flow. On Android and iOS the app ends. On the desktop and the boards, the screen fed by that observer stops following and keeps its last value until a restart.

**What makes a read fail:**
- The known cause is the collections in `ChatRepo` without a lock, which `ObserveMeshChannelPeople` already works around (it skips a refresh that collides with a write).
- Others are the secure store on Apple (a read while it is locked) and a store that cannot be decoded.

| Option | Android, iOS | Desktop, boards | What the user sees | Fit with D4 | Cost |
|---|---|---|---|---|---|
| **A. End, as today** | The app ends | The screen stops following | A crash, or a frozen value | Yes | None |
| **B. Log and skip that read; keep observing** | No crash | It keeps following | The previous value until the next matching event; nothing at all until then if the first read failed | Yes: read on start, read again on a matching event; a failed read is a skipped read. It is the pattern `ObserveMeshChannelPeople` already has. | A `catch` around each read in the 23 observers that lack one (rethrow cancellation, catch `Exception` only, log). `ObserveMeshChannelPeople`, the 24th, already has it. One test each: "a failed read is skipped, and the next event reads again". Domain only, so the cloud can build it. |
| **C. Emit a failure value** (`Flow<Outcome<T>>` or a model with a "read failed" case) | No crash | It keeps following | A text where the value would be | It changes every observer's result type, so every name and model changes too (D34, D35) | Every observer and every collector in 10 view models; texts for flags such as "has notes" mean little. Mostly local. |

A variant of A: each view-model collector gets `.catch { log }`. The app no longer ends, but the screen stops following everywhere, which is what the desktop does today. It is a view-model change for the same partial result.

**Recommendation: B.**
- It removes the crash on Android and iOS, and on the desktop and the boards it keeps the screen following.
- It needs no new types.
- It is domain only.
- It generalises a rule one observer already lives by.

**Its cost:** a failure that repeats on every read is hidden behind a stale value. The log line is the only trace. The root cause, the unlocked collections, stays on its own task (`STATUS.md` Next).

**One question for the owner (Q-C):** 23 copies of the same `try`, or one small helper in `domain/base`? An earlier slice said "no shared helper", but that was about observation in general, not about this catch.

## Found on the way, not part of D5

Each is for the owner to file or drop.

1. **The repository's `setChannelPassword` never updates the channel's commitment** (`ChatRepo.kt:1924-1929`, checked). Only creating a channel with a password (`:2970`) and its metadata (`:2855`) set it. After a `/pass` on an existing channel, the domain still sees no password.
2. **`/j` can never join an existing protected channel.** `ChatCommand.Join` has no password (checked), so the answer is always "wrong password". `JoinChannel` also subscribes and writes metadata before it checks the password (`JoinChannel.kt:71`).
3. **Sends that report success without sending:**
   - a named-channel send without an event id or a Nostr identity (`ChatRepo.kt:3130/3136`);
   - a geohash send while the Tor gate is closed (`:647`).
4. **`/msg` switches to the DM before it sends** (`ChatViewModel.kt:608/646`). A failure then lands on the previous screen's view model.
5. **After a wipe that fails midway, the barrier lets commands in again over half-cleared stores** (`ChatNotices.reset`'s `finally`).
6. **Apple Tor:** if a manager call threw inside `TorLifecycleCoordinator.runStateMachine` (`:93/:98`), `reconcile()` would wait forever (`:63-64`), holding the route lock. No throw was found there today.
7. **The two leave paths run in opposite orders** (`MainViewModel.kt:461-462`, `ChatViewModel.kt:481-482`), so a failure leaves different states behind.
8. **Two misleading test names in `ProcessChatCommandTest`:**
   - "rejects join command outside mesh" asserts `Parsed`;
   - "rejects favorite command outside location" asserts `NotACommand`.

## Questions for the owner

- **Q-A. The store failure:** one base failure, `Failure.StoreUnavailable(reason)`, next to `NetworkError` and the other REST failures, or a `NotSaved` in each feature's sealed type (D23)? Recommended: the base failure. The cause and the remedy are the same whichever feature writes, and only the view's sentence differs.
- **Q-B. The identity failure:** carry `reason` and `remedy` as the data layer words them, or an enum of refusal kinds with the text in the view model (D24)? Recommended: carry them as they are. They are the one place a platform names its own remedy, and a second copy of that text would go stale.
- **Q-C.** Part 2's catch: 23 copies, or one helper in `domain/base`.
- **Part 2:** A, B or C. Recommended: B.
- **Part 3:** which slices, in what order.
